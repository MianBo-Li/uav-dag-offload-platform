# 面向无人机边缘计算的 DAG 任务卸载调度系统 - 项目立项文档

## 1. 项目名称

面向无人机边缘计算的 DAG 任务卸载调度系统

## 2. 项目背景

在无人机巡检、灾害监测、目标识别等场景中，单架无人机常常需要完成图像采集、目标检测、路径分析、结果上传等一系列计算任务。由于无人机自身存在算力有限、电量有限、网络不稳定等约束，部分任务需要卸载到边缘服务器或其他计算节点执行。

本项目要解决的问题是：如何根据任务依赖关系、节点资源状态、网络状态和调度策略，生成合理的任务执行方案，并在系统层面完成任务下发、执行、回传、重试和评估。

## 3. 问题定义

系统接收用户提交的 DAG 任务图，采集无人机与边缘节点的状态信息，依据调度策略生成任务卸载方案，并将子任务分配到无人机本地或边缘节点执行。系统需要记录任务生命周期、异常情况和核心评估指标。

### 输入

- DAG 任务定义
- 无人机状态：电量、CPU、内存、位置、网络质量
- 边缘节点状态：CPU、内存、负载、可用队列
- 调度策略配置

### 输出

- 任务调度计划
- 子任务执行结果
- 完整任务状态流转记录
- 耗时、能耗、失败率等评估指标

## 4. 项目目标

### 核心目标

1. 支持无人机和边缘节点注册、心跳和状态上报。
2. 支持 DAG 任务创建、依赖校验和任务状态管理。
3. 支持调度器根据资源状态生成卸载方案。
4. 支持模拟 Worker 执行任务并回传执行结果。
5. 支持失败重试、超时控制和离线检测。
6. 支持执行记录查询和基础指标统计。

### 扩展目标

1. 支持多种调度策略对比。
2. 支持 MQTT / gRPC 等更贴近真实设备的通信方式。
3. 支持 Prometheus / Grafana 监控。
4. 支持 OpenTelemetry 链路追踪。
5. 支持 Docker Compose 一键启动。

## 5. 使用场景

### 典型场景

1. 无人机上线并持续上报状态。
2. 边缘节点上线并上报资源负载。
3. 用户提交一个包含依赖关系的巡检任务。
4. 系统为每个子任务生成执行位置和顺序。
5. Worker 执行任务并回传结果。
6. 用户查看任务执行记录和性能指标。

### 目标用户

- 学习软件工程的个人开发者
- 算法与系统结合的课程项目使用者
- 边缘计算/调度算法实验平台使用者

## 6. 项目范围

### 本期实现

- 后端 API
- 数据库设计
- 节点管理
- DAG 任务管理
- 调度器
- 模拟执行器
- 结果记录与查询
- 基础测试
- Docker 部署

### 本期不做

- 真实无人机飞控控制
- 复杂前端大屏
- 工业级高可用架构
- 大规模强化学习训练闭环

## 7. 技术路线

### 第一阶段：主闭环

- `FastAPI`
- `PostgreSQL`
- `SQLAlchemy 2.0`
- `Alembic`
- `Redis`
- `pytest`

目标：完成任务提交、节点注册、调度、执行、回传、查询的完整闭环。

### 第二阶段：异步与通信

- `RabbitMQ`
- `Celery`
- `MQTT`

目标：把执行、状态回传和消息流转做得更接近真实系统。

### 第三阶段：工程化

- `Docker Compose`
- `Prometheus`
- `Grafana`
- `OpenTelemetry`

目标：补齐监控、部署、日志、性能观测能力。

## 8. 核心模块

1. 节点管理模块  
   负责无人机和边缘节点注册、心跳、资源上报、离线检测。

2. DAG 任务模块  
   负责任务创建、依赖校验、状态流转、结果存储。

3. 调度模块  
   负责根据任务图与节点状态生成执行计划。

4. 执行模块  
   负责模拟任务执行、失败上报、结果回传。

5. 评估模块  
   负责统计耗时、成功率、重试次数、资源利用率等指标。

6. 平台管理模块  
   负责接口文档、日志、配置和基础运维能力。

## 9. 验收标准

1. 能注册节点并持续上报状态。
2. 能提交合法 DAG 任务。
3. 能生成调度方案。
4. 能执行任务并回传状态。
5. 能处理失败、超时和节点离线。
6. 能查询完整执行记录。
7. 能通过 Docker Compose 启动整个系统。
8. 至少支持三种调度策略对比。

## 10. 风险与对策

| 风险 | 对策 |
| --- | --- |
| 项目范围太大 | 先做最小闭环，再逐步扩展 |
| 算法难度过高 | 先规则调度，再做启发式，再考虑学习型策略 |
| 没有真实设备 | 用模拟 Agent 代替，接口预留真实设备接入点 |
| 系统过于分散 | 先用模块化单体，不急着拆微服务 |

## 11. 当前结论

本项目适合作为一个长期学习型项目。最优策略不是一开始追求“完整”，而是先把主闭环跑通，再逐步把真实场景需要的能力补上。
