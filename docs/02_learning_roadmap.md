# 项目学习与交付路线图

## 总原则

先做闭环，再做增强。先学能用的主流技术，再补工程化和观测能力。

## 第 0 步：定边界

### 要做的事

- 写项目立项文档
- 明确目标用户和真实场景
- 划定本期范围和不做范围

### 产出

- `docs/01_project_proposal.md`

### 完成标准

- 能用 1 分钟讲清楚项目是干什么的
- 能用 1 页纸写清楚系统边界

## 第 1 步：需求分析

### 要做的事

- 列出业务需求
- 列出非功能需求
- 画主流程
- 识别异常路径

### 产出

- 需求清单
- 用户故事
- 流程图

### 完成标准

- 知道用户怎么用
- 知道系统怎么失败
- 知道系统怎么恢复

## 第 2 步：总体设计

### 要做的事

- 设计模块划分
- 设计数据流
- 设计接口边界
- 选择技术栈

### 产出

- 架构图
- 模块图
- 技术选型说明

### 完成标准

- 能说明每个模块负责什么
- 能说明模块之间怎么通信

## 第 3 步：详细设计

### 要做的事

- 设计数据库表
- 设计状态机
- 设计 API
- 设计调度器接口

### 产出

- ER 图
- API 文档
- 状态机图

### 完成标准

- 数据怎么存清楚了
- 状态怎么流转清楚了
- 接口怎么调用清楚了

## 第 4 步：实现主闭环

### 要做的事

- 先实现最小可运行版本
- 先做单体，不急着拆服务
- 先跑通提交、调度、执行、回传

### 建议顺序

1. 节点注册
2. DAG 任务创建
3. DAG 校验
4. 调度器输出计划
5. Worker 模拟执行
6. 状态回传
7. 结果查询

### 完成标准

- 能演示完整流程
- 每一步都可被接口触发

## 第 5 步：补测试

### 要做的事

- 单元测试
- 接口测试
- 集成测试
- 异常测试

### 产出

- 测试用例
- 测试报告

### 完成标准

- 主要逻辑有覆盖
- 异常路径有验证

## 第 6 步：工程化

### 要做的事

- Docker Compose
- 配置文件化
- 日志规范化
- 监控指标
- 接口文档整理

### 产出

- 可启动环境
- 部署说明
- 监控看板

### 完成标准

- 新机器能启动
- 别人能复现

## 第 7 步：增强与创新

### 可选增强

- MQTT 接入
- gRPC 接入
- Prometheus / Grafana
- OpenTelemetry
- 更复杂的调度策略
- 算法对比实验

### 完成标准

- 能体现项目亮点
- 但不破坏主闭环稳定性

## 推荐节奏

### 第 1 周

- 完成立项文档
- 完成需求分析
- 画出主流程图

### 第 2 周

- 完成架构设计
- 完成数据库设计
- 完成 API 草案

### 第 3-4 周

- 实现主闭环
- 跑通模拟执行

### 第 5 周以后

- 补测试
- 补工程化
- 补监控和对比实验

## 当前进度校准

截至 2026-06-08，项目已经越过早期文档设计和主闭环实现阶段，当前已完成：

```text
立项
-> 需求分析
-> 系统设计
-> 数据库设计
-> API 设计
-> 后端骨架
-> 节点管理
-> DAG 任务管理
-> 调度计划生成
-> 模拟执行与结果回传
-> 指标统计
-> Docker Compose
-> Prometheus / Grafana
-> RabbitMQ / Celery 异步执行
-> 失败模拟、业务重试和 Celery 自动重试
-> 并发执行结果幂等锁
-> Worker/队列监控指标
-> 任务取消与 Worker 执行协调
-> Worker 心跳第一版
-> 保存 Celery task id 与安全 revoke
```

当前最应该做的是：

1. 阶段性整理当前 Celery task id 记录和安全 revoke 成果，保证测试、文档和 Docker 配置验证一致。
2. 做一次清晰提交或 PR，把这一阶段成果固化下来。
3. 进入下一阶段增强：Worker 周期性取消检查、死信队列和告警。

后续开发应继续遵循：

```text
先闭环
-> 再测试
-> 再工程化
-> 再增强真实分布式能力
-> 最后再引入更复杂算法和实验
```
